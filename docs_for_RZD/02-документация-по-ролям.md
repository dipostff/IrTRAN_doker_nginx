# Руководство пользователя по ролям (ОТРЭД / IrTRAN)

Это не «официальная инструкция РЖД», а практичное описание того, как приложение реально устроено в коде: какие пункты меню есть, что видно студенту, что открывается только преподавателю и что может админ. Если твоя инсталляция отключила модуль или роль — просто вычеркни соответствующий абзац.

Роли в Keycloak (realm): **`student`**, **`teacher`**, **`app-admin`**, **`dictionary-admin`**. На фронте доступ к страницам режется в `router/index.js` через `keycloak.js` (`isStudent`, `isTeacher`, …).

---

## Студент

### Как попасть в систему

Регистрация и вход идут через **Keycloak**, не через «свою» форму в базе приложения. На стартовой странице (`/`, `AuthorizationView`) ты жмёшь вход — открывается форма Keycloak. Если администратор включил саморегистрацию в realm — можно зарегистрироваться самому; иначе учётку создаёт админ и выдаёт логин/пароль.

После успешного входа тебя обычно перекидывает в **главное меню** (`/menu`, `MenuView`).

### Что на главной

Меню — это набор плиток/ссылок на учебные модули. По коду роутера там, в частности:

- Заявка на грузоперевозку, накладная, акты, памятка, ведомости.
- Список своих документов (`/documents/list`).
- Режим теста (SurveyJS).
- Справочник файлов, сценарии обучения (новичок/продвинутый), тренажёры.
- Уведомления, «Сообщить об ошибке», иногда «Успеваемость» — зависит от того, что включено и куда пускает guard.

Частая путаница: **«чистый» студент** vs пользователь с лишними ролями. В коде есть `isPureStudentAccount` — от этого может зависеть, показывается ли что-то «педагогическое». Если вдруг видишь лишнее — проверь роли в Keycloak.

### Что студент может делать

- Заполнять учебные документы в модулях (формы с привязкой к справочникам: станции, грузы, контрагенты…).
- Сохранять черновики, открывать из списка документов, часть типов — отправлять на проверку преподавателю (модуль **«Проверка документов»** на стороне препода начинается с твоей отправки через API `document-review`).
- Проходить тесты, смотреть результаты и ошибки.
- Качать/смотреть материалы справочника, гонять сценарии.
- Писать багрепорты.

### День из жизни (типичный сценарий)

1. Вошёл через Keycloak → меню.
2. Открыл **«Заявка на грузоперевозку»**, выбрал станции и контрагентов из справочников, добавил отправки и график.
3. Сохранил документ → он появился в **«Загрузка и выгрузка документов»**.
4. По заданию преподавателя нажал **отправить на проверку** (если доступно в UI для этого типа).
5. Зашёл в **«Режим теста»**, прошёл попытку, посмотрел процент и разбор ошибок.
6. В конце дня заглянул в **уведомления** — там могут быть дедлайны или ответ по проверке документа.

## Преподаватель

### Чем интерфейс отличается от студенческого

Роль **`teacher`** (и часто **`app-admin`**) открывает дополнительные пункты:

- **Панель преподавателя** (`/teacher-dashboard`) — обзор студентов, тестов, сценариев (см. `TeacherDashboardView`).
- **Проверка документов** (`/document-review`, `TeacherDocumentReviewComponent`) — очередь отправок, алгоритм, ручная проверка, эталонные шаблоны.
- **Ручная проверка одной отправки** в отдельной вкладке (`/document-review/manual/:id`, `TeacherDocumentReviewManualView`) — удобно для печати/второго монитора.
- Конструктор тестов и банк вопросов живут внутри **«Режим теста»** (`TestModeView` с вкладками) — студент туда либо не пускается, либо видит другое содержимое.

Кстати: преподаватель **не «логинится в другой сайт»** — тот же SPA, те же Keycloak-учётки, просто больше realm-ролей.

### Материалы, задания, группы

В этом проекте «группы» студентов для проверки документов завязаны на **группы Keycloak**, которыми владеет преподаватель (`listTeacherOwnedGroups` на бэкенде). То есть завести группу и накидать студентов нужно в Keycloak (или админом через панель, если так настроено).

Материалы:

- **Справочник** — загрузка файлов (контент-модуль).
- **Сценарии** — набор кейсов для учебы.
- **Тесты** — вопросы, варианты, сборка теста, порог сдачи, число попыток — через интерфейс преподавателя в модуле тестов.

### Как отслеживать прогресс

- Таблицы попыток и проценты в панели преподавателя.
- Статусы прохождения сценариев (снимки/сессии на бэкенде — см. модели `BeginnerScenarioSession`, `TrainingScenarioSnapshot` и т.п.).
- Модуль **проверки документов**: статус отправки (`submitted` / `reviewed`), оценка, комментарий, audit trail по версиям.

### Типичный рабочий день преподавателя

1. Проверил **уведомления** — студент отправил документ.
2. Зашёл в **«Проверка документов»**, открыл отправку, при необходимости прогнал **алгоритм** и сверил с глазами.
3. Заполнил шаблон эталона для типа документа (если ещё не заполнен) — чтобы автопроверка была стабильной.
4. Выставил **вердикт** (принято/нет, оценка, можно ли переделать).
5. Во второй половине дня — **конструктор теста** или правка банка вопросов под новую лекцию.

## Администратор приложения (`app-admin`)

### Полномочия по сути

Роль **`app-admin`** — это «владелец тренажёра» в рамках приложения:

- **Панель управления** (`/admin-panel`, `AdminPanelView`): список пользователей из Keycloak, поиск, назначение ролей **`student`**, **`teacher`**, **`dictionary-admin`** (снятие тоже). Создание пользователей через API `POST /api/admin/users`.
- Доступ к сервисным разделам, которые студенту не нужны: полная картина **багрепортов**, возможно расширенные отчёты.
- В проверке документов админ часто видит **всех студентов**, а не только своих (на бэкенде `isAdmin` снимает фильтр по группам).

Отдельно: **`dictionary-admin`** может крутить **«Заполнение справочников»** без полного админа; но `app-admin` тоже туда пускается (см. guards на фронте и middleware на `/api/dictionaries`).

### Пользователи и роли — на что смотреть

- Всё критичное делается в **Keycloak**; приложение не хранит пароли.
- Если пользователь «есть в БД», но не может войти — смотри учётку в Keycloak и клиент `irtran-client` (redirect URI, PKCE, срок жизни токена).
- Код **`TEACHER_UPGRADE_CODE`** на бэкенде — защита от самовольного повышения до преподавателя через публичный эндпоинт (если используется в вашей сборке).

### Эксплуатация

- **Docker:** healthcheck Keycloak, зависимости `depends_on`, таймауты nginx — типичные места, где «всё упало» после обновления. См. `docker-compose.yml` и комментарии про curl/wget в образе.
- **Импорт больших справочников:** нужны свежий фронт (чанки `import-batch`), лимит тела JSON на бэкенде и адекватные таймауты прокси.
- **Диск:** тома `reference_uploads`, `scenarios_uploads` — не теряй при пересоздании контейнера без бэкапа.
- **Миграции MySQL:** при медленном старте БД смотри логи бэкенда и переменные ретраев миграций.

### Типовые задачи

| Задача | Куда идти |
|--------|-----------|
| Завести студента | Админ-панель → создать пользователя → роль `student` |
| Сделать коллегу преподавателем | Назначить роль `teacher` + завести группу в Keycloak при необходимости |
| Починить «502 сразу после up» | Логи Keycloak/nginx, healthcheck, не начинать нагрузку до `healthy` |
| Студент не видит справочник | Роль `dictionary-admin` / данные в MySQL / ошибка API в Network |
| Проверка документов пустая у препода | Студент не в группе преподавателя или не та роль |

## Мелкие советы всем

- **Кэш браузера** после деплоя фронта — классика: старый чанк JS = старый API (например, вместо `import-batch` уходит старый `/import`).
- Если в интерфейсе везде **401** — сначала обнови токен/перелогинься, потом уже копай бэкенд.
- Документация разработчика по стеку и API — файл `01-техническая-документация.md` в этой же папке.
