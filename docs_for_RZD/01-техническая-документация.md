# Техническая документация (IrTRAN / ОТРЭД)

Документ для разработчиков, которые впервые открыли репозиторий `IrTRAN_doker_nginx`. Ниже — как всё устроено, где что лежит и как не сломать прод.

---

Архитектура в двух словах

Классическая трёхзвенка под Docker (или локально):

1. Фронт — Vue 3, собирается Vite, отдаётся nginx-контейнером или `npm run dev`.
2. Бэк — Node.js + Express. Внутри смешаны два стиля API (об этом ниже).
3. Данные — MySQL 8 (основная БД приложения), плюс PostgreSQL только для Keycloak.

Аутентификация — Keycloak (JWT). Бэкенд валидирует токен через JWKS; часть админских операций ходит в Keycloak Admin REST API.

Nginx перед приложением проксирует `/api` на бэкенд, раздаёт статику фронта, поднимает таймауты для тяжёлых операций (импорт справочников и т.п.).

**Важно:** не путать два API-стиля:

- **Legacy:** `POST /stations`, `POST /requests_transportation`, … — тело вида `{ "act": "read"|"create"|..., "selection_type": "all"|"one", "object": { ... } }`. Список путей задаётся в `config/restapi.json`, обработка идёт через `WorkerController` и дочерние процессы.
- **Современные REST:** префикс `/api/...` — обычные `express.Router`, часто с `keycloakAuth.verifyToken()` и проверкой realm-ролей.

Фронт в `helpers/API.js` активно использует **оба**: для справочников и CRUD документов — legacy `sendRequest`, для новых фич — `apiClient.get/post/...` на `/api/...`.

## База данных и модели

ORM — **Sequelize**, диалект **MySQL**.

**Справочники и транспортный домен** (фрагмент `src/models/`):

- `Station`, `Countrie`, `LegalEntities`, `Cargo`, `CargoGroup`, `Payer`, `PayerType`, `Sending`, `SubmissionSchedule`, `SendNumber`, `Contract`, `Ownership`, `OwnerNonPublicRailway`, `RollingStockType`, `SendType`, `SpeedType`, `MessageType`, `SignSending`, `MethodSubmission`, `DocumentType`, `DestinationIndication`, `TransportPackageType`, `ApprovalWithOwner` и др.

**Прикладные / учебные сущности:**

- `RequestTransportation` — заявка на грузоперевозку (в т.ч. связи с отправками, графиком, плательщиками через id-массивы или ассоциации — смотри актуальную модель).
- `StudentDocument` — универсальное хранилище черновиков/документов студента с `document_type` и JSON `payload`.
- `DocumentReview`, `DocumentReviewTemplate` — модуль проверки документов (отправка на проверку, шаблоны, статусы).
- `Test`, `TestVariant`, `TestQuestion`, `TestAttempt`, … — тестирование.
- `ReferenceDocument`, `Scenario`, снимки тренажёра, уведомления, багрепорты, дедлайны обучения — см. `migrations/` и имена моделей.

Схема БД эволюционирует через файлы в `irtran_server-main/src/migrations/`. При старте в Docker миграции ретраятся (переменные `MIGRATION_MAX_RETRIES`, `MIGRATION_RETRY_DELAY_SEC`).

## API: что дергать и как

### Legacy POST (общий паттерн)

**Маршрут:** любой из `config/restapi.json` (например `/stations`, `/cargo`, `/requests_transportation`).

**Тело:**

```json
{
  "act": "read",
  "selection_type": "all"
}
```

или для одной записи:

```json
{
  "act": "read",
  "selection_type": "one",
  "object": { "id": 123 }
}
```

**Ответ:** обычно массив записей или один объект — зависит от обработчика в воркере.

**Авторизация:** если в `config/app.json` включён `enable_auth`, на эти POST вешается `keycloakAuth.verifyToken()`.

### Примеры REST `/api` (не исчерпывающий список)

**Справочники (модуль Dictionary):**

- `GET /api/dictionaries` — список доступных справочников (метаданные).
- `GET /api/dictionaries/:key/meta` — колонки, типы.
- `GET /api/dictionaries/:key/rows?limit=&offset=` — страница строк + `total`.
- `POST /api/dictionaries/:key/rows` — создать строку (валидация типов).
- `PATCH /api/dictionaries/:key/rows/:id` — обновить.
- `DELETE /api/dictionaries/:key/rows/:id` — удалить одну.
- `POST /api/dictionaries/:key/rows/delete-batch` — массовое удаление по id.
- `POST /api/dictionaries/:key/import-batch` — пакетный импорт JSON `{ "rows": [...] }` (большие объёмы режутся на фронте).

Доступ по ролям см. в `dictionaryRoutes.js` (часто `dictionary-admin` и/или `app-admin`).

**Проверка документов (`documentReviewRoutes.js`):**

- `POST /api/document-review/submit` — студент отправляет документ (тело: `source`, `documentId`, …).
- `GET /api/document-review/my` — мои отправки.
- `GET /api/document-review/teacher/submissions` — очередь преподавателя (фильтры в query).
- `GET /api/document-review/teacher/submissions/:id` — детали.
- `GET .../audit-trail` — история версий.
- `GET /api/document-review/teacher/metrics` — метрики.
- `GET /api/document-review/templates`, `PUT /api/document-review/templates/:documentType` — эталонные шаблоны.
- `POST .../analyze` — алгоритмическая проверка.
- `PATCH .../finalize` — финальное решение преподавателя (принято/нет, оценка, комментарий).

Роли: студент / `teacher` / `app-admin` — проверки внутри роутера (`keycloakAuth`, `hasRealmRole`).

**Админка (`adminRoutes.js`):**

- `GET /api/admin/users?q=` — пользователи Keycloak + роли.
- `POST /api/admin/users` — создать пользователя.
- Назначение/снятие ролей — см. остальные маршруты файла.

Все под `requireRealmRole('app-admin')`.

Полный перечень REST лучше смотреть grep’ом по `register*Routes` и `router.get/post` в соответствующих файлах — в одном README всё быстро устаревает.

## Локальный запуск

Кратко (детали ещё в корневом `README.md` и `DOCKER.md`):

1. Поднять MySQL + Keycloak (удобнее `docker compose up -d` из корня репозитория).
2. **Бэкенд:** `cd irtran_server-main && npm install && node app.js`  
   Указать в окружении доступ к БД и Keycloak (см. ниже).
3. **Фронт:** `cd IrTRAN-main && npm install && npm run dev`  
   В `.env` или переменных Vite: `VITE_API_URL`, `VITE_KEYCLOAK_*`.

Регистрация клиента `irtran-client` в Keycloak и redirect URI для dev — пошагово описаны в `README.md` (раздел про Keycloak).

## Переменные окружения и конфиги

**Docker / production (фрагмент из `docker-compose.yml`):**

- `MYSQL_*`, `DATABASE_*` на бэкенде.
- `KEYCLOAK_AUTH_SERVER_URL` — URL, который видит браузер (issuer).
- `KEYCLOAK_JWKS_URL` — внутренний URL до Keycloak из контейнера бэкенда.
- `KEYCLOAK_REALM`, `KEYCLOAK_RESOURCE` (client id).
- `KEYCLOAK_ADMIN`, `KEYCLOAK_ADMIN_PASSWORD` — для Admin API.
- `TEACHER_UPGRADE_CODE` — секрет для повышения до преподавателя (см. auth routes).
- `REFERENCE_UPLOAD_DIR`, `SCENARIOS_UPLOAD_DIR` — тома загрузок.
- `MIGRATION_MAX_RETRIES`, `MIGRATION_RETRY_DELAY_SEC`.

**Бэкенд HTTP:**

- `HTTP_JSON_BODY_LIMIT_MB` — лимит JSON (по умолчанию 50), важно для `import-batch`.

**Справочники (сервер):**

- `DICTIONARY_ROWS_MAX_LIMIT`, `DICTIONARY_DELETE_BATCH_MAX_IDS` — пагинация и батчи удаления (см. `dictionaryRoutes.js`).

**Фронт (Vite):**

- `VITE_API_URL` — база API (часто тот же origin, что и приложение, если nginx проксирует `/api`).
- `VITE_KEYCLOAK_URL`, `VITE_KEYCLOAK_REALM`, `VITE_KEYCLOAK_CLIENT_ID`.
- `VITE_DICTIONARY_IMPORT_CHUNK` — размер чанка импорта в браузере (если задан).

Статические JSON-конфиги бэкенда: `irtran_server-main/config/app.json` (порт, HTTPS, `enable_auth`), `restapi.json` (legacy пути), `worker.json`.

## Известные ограничения и технический долг

- **Два параллельных API** (legacy POST + `/api`) — новичку легко добавить фичу «не туда». Новое логичнее вешать на `express.Router` под `/api`, но справочники и старый CRUD всё ещё живут на воркерах.
- **Keycloak `latest`** в compose — воспроизводимость образов страдает; для прод лучше закрепить версию.
- **CORS в `Server.js`** выставлен широко (`*`) — для публичного интернета обычно ужимают до конкретных origin.
- Тяжёлые зависимости бэкенда (Puppeteer, Aspose и т.д.) — развёртывание и лицензии нужно учитывать отдельно.
- Часть фронта смешивает Bootstrap и Vuetify — исторические слои, не ждите единого UI-kit.
- Документация в коде неравномерная: критичные места (импорт словарей, review документов) лучше читать по файлам, а не по одному README.
